# SOLQ COMMAND — 이메일 인증 기반 고객 신청 구현 지시 (2026-11-12)

발행 ATLAS. 사용자 승인: 이메일 인증 → 신청서 작성 → 접수번호 발급 → 인증 이메일 접수 확인. 기존 SOLQ 개발 브랜치 `dev/solq-customer-chat-pricing-20261112`, 이슈 #10, 기존 고객 플랫폼 후보 코드와 검증 증거를 이어서 사용한다. 운영 변경 NO-GO.

## 요구 기능
1. 홈페이지 첫 방문, 서비스 안내, 일반 문의 및 공개 AI 상담은 비로그인 가능. **제작·서비스 신청서 제출은 인증된 이메일 세션에서만** 허용하는 신규 경로 개발.
2. 비밀번호 없는 이메일 OTP 또는 매직링크 인증을 우선 검토. 서버가 Supabase Auth `getUser`로 유효 사용자와 확인된 이메일을 검증하고, 이메일을 임의 클라이언트 입력으로 신뢰하지 않는다.
3. 인증 성공 후 신청서 작성. 서버에서 검증된 이메일·인증 UID와 기존 신청 내부 ID를 신뢰된 트랜잭션/서버 경로로 결합한다. 기존 receipt-only 익명 경로로 소유권을 추정하거나 claim하지 않는다.
4. 신청 저장 성공 후 서버가 접수번호 발급. **저장 성공 확인 뒤** 인증된 이메일로 접수 사실·접수번호·안전한 조회 안내를 전송할 수 있도록 이벤트/아웃박스·중복 방지·재시도·발송 실패 표시 설계. 신청 저장 성공과 이메일 발송 성공을 혼동하지 않는다. 이메일에는 민감한 신청서 본문·접근 증명·비밀 토큰을 포함하지 않는다.
5. OTP/링크 남용·재전송 제한, 인증 만료, 이메일 변경, CSRF/Origin, 중복 신청, 계정 전환, 고객 A/B 접근, 이메일 발송 실패, 재시도 및 수신거부와 무관한 거래성 알림 분류를 테스트.
6. 개인정보 처리방침에 인증 이메일, 발송 목적, 보관·삭제, 국외 처리 위탁/이전 요건을 실제 운영 환경 기준으로 점검. 30일 자동삭제 임의 추가 금지.
7. 기존 관리자 무료 계획 → 견적 동의 → 입금 확인 → 별도 제작 승인 순서와 가격/비용 관문 유지.

## 작업 순서 및 게이트
A. 현재 Auth 이메일 provider/SMTP/템플릿/발송 한도·과금 여부를 **읽기 전용** 조사하고 비용 0원 또는 기존 범위 내인지 판정. 운영 Auth 설정 변경 금지.
B. 기존 `submit_application` 및 프런트엔드 신청 코드 호출 경로를 조사. 기존 익명 신청의 고객 차단 없이 **개발 브랜치에서** 인증 기반 신규 경로 구현.
C. 합성 Auth 세션·PostgreSQL 격리 환경에서 정상/악의적 요청, 고객 A/B, 일회용 인증·연계, outbox idempotency 및 실패 재처리 테스트. 기존 49+57 PASS 증거 재사용.
D. 실제 Auth·PostgREST E2E는 안전한 테스트 환경과 발송 승인/비용 검토 후에만 실시. 실제 운영 DB INSERT/DDL, Auth 계정 생성, OTP·접수 메일 발송, 고객 통지, Edge 배포, 유료 API, 신규 서버 및 운영 배포는 **별도 명시 승인 전 중단**.
E. 보안 경고 7건, 백업·격리 복원, RPO/RTO 및 롤백 관문 NO-GO 유지. 인증 신규 경로가 검증되기 전 기존 운영 `submit_application`의 익명 권한을 REVOKE하지 않는다.
