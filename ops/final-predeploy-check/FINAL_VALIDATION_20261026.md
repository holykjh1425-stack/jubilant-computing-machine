## 1. 세션 충돌·권한 문제 해결

다른 Work 세션의 종료 상태는 계속 확인 불가다. 기존 세션 종료를 추측하거나 강제 종료하지 않았다. 대신 사용자가 허용한 '독립적인 대체 검증 환경'을 사용했다.

Actions 실행 40318383219는 별도 GitHub 호스팅 VM에서 실행됐고, 테스트 DB 컨테이너명은 실행 ID/시도 번호로 유일하다. Docker inspect로 network=none, 공개 포트=0, 호스트 bind mount=0을 확인했다. DB 시작 시 public 테이블=0을 확인한 다음 저장소 SQL과 가상 데이터만 적재했다. 운영 접속 URL·DB 자격증명·고객 원문을 전달하지 않았고, 권한 상승·기존 Work 로컬 설치 재시도도 하지 않았다. contents:read 권한만 사용하고 checkout 자격증명은 유지하지 않았다. 각 검증 컨테이너 삭제 단계도 success다.

과거 setgroups/seteuid 오류를 같은 환경에서 반복하지 않고, 별도 격리 실행 환경으로 문제를 해결했다. 이는 과거 Work 설치 오류나 화면 깜빡임 원인을 모두 복구했다는 뜻은 아니다.

## 4. 실제 PostgreSQL RLS — 격리 정책 검증 통과

[RLS 실행·로그](https://github.com/holykjh1425-stack/jubilant-computing-machine/actions/runs/40319012831), 코드 4df6e76, job 121558840100. 결과: rls-integration-result.json.

저장소에 있는 관리자·신청·계획·작업 조회 정책을 실제 PostgreSQL의 anon/authenticated 역할로 실행했다. auth.uid는 가상 SQL 식별값으로 설정했으며 실제 서명된 JWT 검증은 아니다. 운영 정책의 읽기 전용 목록과 대조해 관리자 membership·익명 신규 신청 조건이 유지됨을 확인했다.

관리자 조회·명시적 상태 변경 허용, 비관리자 행 조회 0·수정 0, 비관리자 계획 INSERT 권한 거부, 익명 SELECT 거부, 잘못된 상태의 익명 INSERT RLS 거부, 동의된 정상 신규 INSERT 허용을 확인했다. 운영 테이블/정책 변경은 0회다.

추가 관측: 운영 admin_users에 anon/authenticated의 TRUNCATE·REFERENCES·TRIGGER 잔여 테이블 권한이 있다. RLS 자체가 이 권한을 제한하지는 않는다. 이것만으로 공개 REST에서 TRUNCATE 호출이 가능하다고 단정하지 않으며 실제 파괴 요청은 보내지 않았다. 운영 반영 전 해당 역할이 직접 SQL/다른 privileged RPC에서 이 권한을 사용할 경로와 불필요 여부를 검토해야 한다. 중복 수정 SQL에 권한 철회를 조용히 추가하거나 운영 권한을 변경하지 않았다.

## 5. 백업·무결성·현재 운영 자산

native 실행에서 가상 DB를 실제 pg_dump한 뒤 별도의 solq_restore DB로 복원했다. 신청·계획·작업 집계와 설치된 가드 트리거 수가 일치했다. 이는 합성 스키마의 dump/restore 실행 증거이며 운영 Auth·확장·Storage·전체 ACL/데이터 내용의 복구 증명은 아니다. 실제 운영 백업의 보호된 확보·복원 확인은 여전히 필요하다.

배포 대상은 release-manifest.json의 관리자 HTML+참조 8개=9개, 서버 3개, SQL 1개=총13개. 이번 제품 파일 변경이 없어 기존 manifest 재생성 결과가 바이트 단위로 동일했다.

운영 URL을 HTTP로만 읽은 결과(live-assets-observation.json): admin.html/SDK/config/free-workflow/admin.js는 200이며, 새 icons/nexus-192.png·admin-base.css·admin-review.css·plan-view.js는 404다. 후보를 아직 배포하지 않았으므로 예상 가능한 상태이며 운영에서 새 관리자 화면이 검증됐다는 뜻이 아니다. 응답한 운영 자산은 max-age=0,must-revalidate 및 ETag를 사용한다. HTML CSP는 메타 방식이므로 HTTP 헤더 목록에 없다는 사실만으로 CSP 부재로 판단하지 않는다.

운영 config.js는 파일 해시는 다르지만 SUPABASE_URL·SUPABASE_ANON_KEY 값이 후보와 동일함을 키를 출력/복사하지 않고 확인했다. 배포 시 운영 config를 우선 보존하고 관련 없는 설정을 덮어쓰지 않는다. SDK는 후보 해시와 동일하다.

## 7. 배포 계획·구체적 잔여 조건

최소 적용 순서는 기존 계획을 유지한다: 보호된 운영 백업 확인 → DB 가드(짧은 잠금·단일 트랜잭션·충돌 시 전체 rollback) → 서버 엔트리/handler/engine → 관리자 9개 자산 원자적 교체 → 구 탭 재접속·해시/CSP/캐시 확인. 견적 API·과거 후보 폴더 전체는 제외한다.

DB 가드가 새 부분 인덱스에서 제외하는 과거 미연결 4개 및 논리적 중복은 보존한다. 연결 중복이 새로 발견되면 자동 삭제하지 않고 중단한다. 롤백은 검증된 조회 전용 화면/유지보수 화면을 사용하고 구 자동 생성 관리자 JS를 재노출하지 않는다. 새 서버 가드 제거·전체 DB 과거 복구는 별도 검토·승인한다. 상세 잠금 순서·timeout·중단 기준은 RECOVERY_HANDOFF.md의 배포 절차를 따른다.

배포 승인 전 남은 해제 조건:

1. 기존 프로젝트의 보호된 실제 관리자 세션과 승인된 합성 인증 계정 환경으로 서명 JWT/세션 만료/비관리자 및 Edge API 통합 확인. 운영 고객 데이터 변경 없이 수행할 수 있어야 한다. 현재 운영 로그인 자격증명/재사용 세션을 확보하지 못했으므로 실행하지 않았다.
2. 운영 DB·함수/ACL/RLS·cron·배포 자산·Edge 버전의 보호된 백업 확보와 승인된 복원 환경에서 복구 실증. 합성 dump 결과만으로 대체하지 않는다. 현재 접속 경로로는 운영 백업 다운로드/복원 검증을 수행하지 않았다.
3. admin_users 잔여 테이블 권한의 사용 경로·필요성 검토 및 필요한 조치 별도 승인.
4. 적용 승인 이후에만 후보 운영 자산의 실제 캐시/CSP/로그인·읽기 무쓰기를 확인. 배포 전 격리 통과와 배포 후 확인을 구분한다. 이 최종 확인은 승인 후 배포 계획의 필수 중단 지점이다.

이번에는 1~3의 접근·보안·운영 승인 경계를 임의로 넘지 않았다. 동시 검증 종료 증거를 반복 조회하거나 이미 통과한 native/SDK/RLS 작업을 다시 실행할 이유는 없다.

**최종 판정: 핵심 동시성 차단 해소·격리 통합 통과 / 운영 배포 보류.** 운영 DB 변경·main 병합·실제 배포·제작·유료 AI 호출은 수행하지 않았다. 다음 작업은 위 잔여 조건의 해결이며 새 환경 설치나 기존 테스트 전면 재실행이 아니다.
