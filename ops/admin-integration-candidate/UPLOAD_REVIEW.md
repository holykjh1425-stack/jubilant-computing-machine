## 운영 위험과 보존

기존 확보 운영본은 관리자 조회/폴링에서 free.plan()/free.assign()을 호출하고 계획 ID 키로 작업을 조회·생성한다. 서버는 신청 ID 키를 사용하므로 중복 작업이 생길 수 있다. 후보는 application_id 및 명시적 plan 연결을 읽는 snapshot()만 제공하고 조회 시 등록·실행을 호출하지 않는다.

이번 공개 JS 최신본 GET은 admin.js/free-workflow.js 모두 HTTP 403으로 실패했다. 따라서 기존 확보본의 위험 분석이며 최신 운영 자산이 그대로인지 독립 재확인하지 못했다. 인증된 운영 관리자 화면을 재현 목적으로 열지 않았다. 후보 보존만으로 운영 위험은 차단되지 않는다.

지금 적용 가능한 운영 절차는 불필요한 운영 관리자 조회/열린 탭의 자동 새로고침을 피하는 것이다. 기술적 차단 후보는 검토한 읽기 전용 관리자 자산과 DB 연결 가드다. 적용은 별도 승인 후 수행한다. 관리자 상태저장 등 명시적 쓰기 기능은 조회와 구분한다.

기준 신청 8·무료 계획 5·작업 5·미연결 4는 이전 읽기 전용 검증 결과다. 이번에는 운영 DB에 접속하거나 재집계하지 않았으므로 현재 수치라고 재확정하지 않는다. 운영 데이터 쓰기·삭제·임의 연결은 수행하지 않았다.

## 운영 인증/API 후속 통합 검증 계획

1. 제공자 disabled 유지와 후보 자산/SQL/API의 정확한 버전 및 적용 여부부터 확인한다. 미배포 후보에 운영 쓰기 요청을 보내지 않는다.
2. 기존 관리자 세션을 우선 사용하되 구 운영 관리자 페이지를 열지 않고 후보의 격리 환경에서 검증한다. 실제 비밀번호/토큰을 저장소·보고서·로그에 남기지 않는다.
3. 운영 인증은 getUser와 관리자 권한 SELECT로만 확인한다. 익명·비관리자는 읽기 접근 거절을 확인하고, 고객별 신청→계획→작업 연결은 SELECT로 검사한다. 고객 응답 본문은 공개 증거에 넣지 않는다.
4. 후보 API의 list 조회는 적용된 경우에만 수행하고 원장별 application_id 필터·유효 견적 판정·네트워크 쓰기 0회 여부를 대조한다. 현재 새 원장이 미적용이므로 이 통합 검증은 미완료다.
5. 발행·동의·입금 증거·수동 확인·제작 승인 같은 쓰기 경로는 격리 가상 DB에서만 시험한다. 운영 트랜잭션 ROLLBACK을 전제로 한 쓰기 시험도 하지 않는다.
6. 승인된 후속 배포 환경에서 실제 CSP·스크립트 순서·캐시 갱신·로그인/로그아웃·PC 및 실물 휴대전화 가독성을 확인한다. 운영 접속 중 기존 데이터에 쓰는 버튼은 누르지 않는다.

## 롤백과 별도 승인

브랜치 업로드는 운영에 영향이 없다. 후보 보존을 되돌릴 때는 해당 변경만 후속 revert 커밋으로 되돌리며 main/운영/고객 데이터에는 손대지 않는다. 브랜치 강제 덮어쓰기를 사용하지 않는다.

향후 배포 전 정확한 호스팅 원본과 DB 함수/ACL/트리거/RLS·데이터의 복구 가능한 백업을 보호된 위치에 확보하고 복구 가능성을 확인한다. SQL 실패는 전체 트랜잭션을 ROLLBACK한다. 배포 후 장애는 제공자 차단·읽기 전용 관리자 유지보수 화면을 유지하면서 변경 항목만 승인된 백업 기준으로 복구한다. 조회 시 쓰는 구 관리자 JS를 복원하지 않는다. 새 증거/원장은 삭제하지 않고 쓰기 경로를 닫아 보존한다. 이전 emergency rollback.sql은 이 변경의 복구 절차가 아니다.

별도 승인 대상: main 병합, 호스팅 자산 반영, Edge 배포, 운영 DB SQL 적용/가드 제거/함수 복원. 실제 견적 발송·입금 확인·제작 승인·제공자 활성화·유료 API·고객 제작은 승인 범위에 포함하지 않는다. 배포 승인 전에 실제 인증/API 통합의 미완료 범위와 검증 방법을 다시 보고한다.
