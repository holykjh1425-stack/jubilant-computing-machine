# SOLQ COMMAND — 백업·복원 검증 한시적 권한 및 최종 승인 관문 지시서

- 발행: ATLAS
- 일자: 2026-11-05
- 수신: CORE · AUTO · GUARD · SENTINEL
- 참조: FIN
- 판정: **NO-GO** (운영 배포 금지)
- 목적: 기존 유효한 실플랫폼 검증 51 PASS / 0 FAIL을 반복하지 않고, 백업·복원·RPO/RTO·보안·기기 회귀 관문을 완성한다.
- 근거: `ops/independent-runner/reports/ATLAS-20261105-backup-access-gates.md`, commit `06d078891fb46c0baf6089552db2d39f0c59686a`.
- 대상: Supabase project `elfacqmvygnwjlklqhiz`; Supabase 조직명 NEXUS LABS 유지; 개발 브랜치 `dev/solq-independent-runner-20261102`.

## 1. 현황 확정

- 실제 PostgreSQL 17.11·Auth/JWT·PostgREST·Edge·업무 통합·동시성에 관한 **기존 비운영 51 PASS/0 FAIL** 로그와 커밋을 유효 증거로 재사용한다. 반증 없이는 재실행하지 않는다.
- 백업 가능성 매트릭스와 Owner 협조 요청은 이미 작성했다. Storage 버킷/객체 0건은 해당 관측 시점의 결과일 뿐 전체 백업 성공 증거가 아니다. 활성 Edge 함수 4개(운영 배포 소스/설정 전체 백업은 미완료).
- 실제 운영 데이터 암호화 덤프 0건, 실제 격리 복원 0건, 실측 RPO/RTO 없음. 운영 보안 경고 7건과 PC·Android·iOS 실제 기기 회귀는 미종결.
- 지원 티켓 SU-536243는 전문 보안팀으로 이관되었고, 새로운 백업·복원 기술 해결책은 확인되지 않았다. 이미 보낸 질문을 중복 발송하지 않는다.

## 2. 한시적 권한 범위

### 이번 지시서로 허용되는 일

- **조회 전용:** 운영 프로젝트 Database → Backups의 복구점 목록·유형·완료 시각·다운로드 가능 여부·백업 범위 조회; 기존 Pro 기능, ACL, Storage/Edge 메타데이터, 공식 복원 절차 확인.
- **안전한 준비:** 기존 승인된 비운영 환경의 격리·네트워크 송신 차단·암호화 저장소 ACL·가용 공간·공개키 지문·TLS CA/호스트 검증; 백업/복원 사전 점검 및 시험용 합성 데이터 작업.
- **검증 작업:** 보유한 적법한 접근 권한 안에서 환경·무결성·로그·권한·기기 회귀 상태 확인; 검증 결과와 차단 증거를 개발 브랜치 보고서에 기록.
- Owner가 이미 승인한 보호된 로컬 반출 방식이 실제로 준비되어 있고 **대상·범위·비용·복구키 책임자·외부 송신 차단이 확정된 때에만** 해당 한정 범위에서 백업·복원 실행. 조건 충족 여부를 기록해야 한다.

### 별도 명시적 승인이 필요한 일

- 신규 유료 Supabase 프로젝트/복제·서버·스토리지 생성 또는 과금 가능한 작업.
- 보호 저장소·복구키 관리가 확정되지 않은 운영 고객 데이터 반출/제3자 보관.
- 운영 DB 쓰기, Auth/RLS/SSL/Secrets/Vault/SMTP/OAuth/보안 설정 변경, 운영 함수 교체, 운영 배포, main 병합, 비밀키 재발급 및 실제 고객 대상 발송.
- 운영 프로젝트에 대한 복원 버튼 실행. 운영을 격리 대상처럼 취급할 수 없다.

### 자격증명·기간

기존 Owner 계정으로 로그인한 세션이 없는 경우, **Owner가 직접 로그인한 화면에서 조회만 수행**하며 비밀번호, DB 연결 문자열, API 키, 개인키를 채팅·GitHub·공개 CI에 전달하지 않는다. 권한은 본 검증 작업의 종료 또는 철회 시 종료하고, 접근 종료/폐기 증거를 남긴다. 워커가 계정 권한을 스스로 확대하거나 대리 승인하지 않는다.

## 3. GUARD — 1차 최우선: Owner 복구점 확인과 전체 백업

1. 기존 매트릭스 항목(DB 데이터/스키마/함수/트리거/RLS/권한/Auth/Storage 메타데이터와 바이트/Edge/SMTP/OAuth/Vault/Secrets)을 `확보 가능`, `부분 확보`, `미확보`로 계속 관리한다.
2. Owner의 기존 Supabase 대시보드 **Database → Backups**에서 최신 복구점 시각, 백업 유형(논리/물리/PITR 등 실제 표시값), 보존 범위, 다운로드 가능 여부를 **읽기 전용으로 확인**한다. 버튼 `Restore`, `Clone`, `Upgrade`, `Reset`은 누르지 않는다.
3. 실제 백업 경로 선택 전에 공식 지원 범위, DB 읽기 접근, TLS verify-full/CA, Windows 보호 저장소, 디스크 여유, 동기화 제외, 공개키 수신자, 비용, 일관된 스냅샷 전략을 점검한다.
4. 허용 조건 충족 시 **평문 덤프 디스크 저장 없이** 승인된 보호 방식으로 전체 DB를 암호화 반출한다. 종료 코드, 시작·종료 시각, 크기, 수신자 공개키 지문, SHA-256, 비밀 없는 manifest, 보호된 보관 위치를 기록한다. 실패·부분 덤프는 PASS 금지.
5. Auth 설정, Storage 파일, Edge 배포 설정 및 Vault/Secrets 등 DB 덤프로 복구되지 않는 구성요소는 **별도 증거와 복구 방법**을 확보한다. 미확보 시 전체 백업 PASS 금지.
6. 복원 대상이 **다른 주소·인증·스토리지·네트워크**인 것을 이중 확인하고, cron/pg_net/webhook/SMTP/AI 공급자·고객 알림 등을 복원 **전에** 차단한다. 공식 Clone이 자동 외부 작업을 유발할 수 있으므로 안전성 확인 없이 생성·복원하지 않는다.
7. 실제 암호화 백업으로 격리 복원하고 테이블·컬럼·함수·트리거·인덱스·RLS·권한·행 내용·시퀀스 및 복호화/서비스 동작을 비교한다. 정확히 일치 또는 사전 승인된 차이만 PASS.
8. **RPO:** 검증 기준 시점과 실제 일관된 백업 시점의 차이를 측정. **RTO:** 복원 시작부터 필수 서비스 기능 검증 완료까지 실측. 목표와 실측을 구분한다.
9. 종료 시 키·접근 권한 회수 및 복원 환경의 보호 보존/안전 폐기 기록. 실제 고객 데이터는 GitHub·Actions·로그·테스트 보고서에 넣지 않는다.

## 4. CORE — 안전한 독립 복원 환경

- 기존 PostgreSQL 17/Supabase 비운영 환경을 우선 재사용하고 운영 연결과 물리적으로/논리적으로 분리된 네트워크·계정·볼륨·프로젝트 식별자를 검증한다.
- 원본 복원 직후 스케줄러나 외부 발송이 실행되지 않도록 선차단한다. 외부 서비스·비밀값은 운영값으로 복제하지 않는다.
- 복원 후 카탈로그·권한·RLS·의존성·Auth 호환성을 비교한다.
- 신규 과금 자원은 생성하지 않는다. 필요 시 목적·최대 비용·종료 조건을 FIN/ATLAS에 보고 후 별도 사용자 승인.

## 5. AUTO — 복원 결과의 최소 기능 회귀

- 복원 격리 환경에서 합성 테스트 고객만 사용해 Auth 관리자 로그인·권한 분리, 신청·문의·무료 계획·견적·수동 입금 확인·별도 제작 승인 및 무단 제작 차단을 확인한다.
- 기존 51 PASS 전체를 반복하지 않고 **복원 후 생존 기능 확인만** 수행한다.
- 실제 고객 메시지·유료 API·제작 실행 0건을 유지한다.

## 6. SENTINEL — 보안 종결

- SECURITY DEFINER 3개 및 공개 호출, `admin_users`의 불필요 관리 권한, 기본/전역 ACL, Security Advisor 기존 7경고, leaked-password protection, 비공개 함수 API/직접 접근 노출을 검토한다.
- 각 항목은 `해결(증거)` / `위험 수용(영향·가능성·보완통제·승인권자 명시)` / `미해결(차단)`로 구분한다.
- 격리 후보 PASS를 운영 경고 해소로 간주하지 않는다. 위험 수용은 워커 단독 결재 불가. 운영 보안 변경은 별도 승인이 필요하다.

## 7. PC·모바일 회귀 — CORE와 GUARD

- PC, Android, iOS에서 메인·신청·문의·견적·관리자 화면을 점검한다. 실기기/실브라우저 검증과 시뮬레이터·서버 테스트를 구별한다.
- Critical 0, High 0이어야 해당 회귀 PASS. 실제 사용할 수 없는 기기는 `미검증`으로 기록하고 Owner 협조 요청 또는 대체 검증의 한계를 명시한다.

## 8. FIN — 비용 승인 관문

- 추가 자원이 필요하면 공급자·서비스·총액/시간당 비용·사용 상한·외부 송신/개인정보 위험·중단 및 삭제 방법을 보고한다.
- 기존 Pro 복구점 **조회는 우선**, 유료 Clone/추가 프로젝트 생성은 명시적 신규 승인이 있을 때만 실행한다.

## 9. OWNER가 수행할 최초 최소 조치

**Supabase 대시보드 로그인 → 해당 프로젝트 → Database → Backups → 최신 복구점, 유형, 날짜, 다운로드 항목 확인.**

백업 버튼이나 복원 버튼을 누르지 말고, 비밀번호/비밀키를 보내지 않는다. 화면에 표시된 **비밀이 아닌 항목만** ATLAS에 전달한다. 대시보드 메뉴명이 달라지면 실제 UI에 맞춰 대응한다.

## 10. ATLAS 최종 승인 관문

- [ ] 기존 51 PASS 근거 보존
- [ ] 백업 범위/암호화/보관 키 책임자 확인
- [ ] 전체 운영 백업 실제 완료 및 SHA-256 무결성 PASS
- [ ] 실제 격리 복원과 DB+외부 구성의 복구 가능성 PASS
- [ ] RPO·RTO 실측
- [ ] 보안 경고 및 권한 위험 종결
- [ ] PC·Android·iOS 회귀 PASS
- [ ] 실제 운영 변경 파일·SQL·설정 목록과 롤백 검증 완료
- [ ] 사용자 **별도 운영 배포 승인** 확보

**GO 신청 가능 조건:** 위 필수 검증 모두 PASS 및 보안 위험이 적법하게 종결되었을 때만 승인 요청. `CONDITIONAL GO`는 잔여 위험의 명시적 보고로 사용하되 자동 배포 허가가 아니다. 미충족 시 **NO-GO** 유지.
