## 실제 운영 화면·소스 근거
- https://solqtech.com/ 화면이 클라우드 데스크톱 브라우저에서 실제 표시됐다. 신청 CTA·양식·2개 필수 동의·가격·정책 링크를 확인했다.
- Sites 버전28의 원본 커밋 `ab4d34c830669e69b57f0689588eb6a24b41f91e` 객체가 기존 로컬 Sites 저장소에 있어 해당 dist 파일을 직접 읽었다. GitHub main 또는 다른 후보를 실제 배포 소스로 가정하지 않았다.
- DOM에서 config.js, api.js, app.js, solq-design.js 로딩 경로를 확인했다. 버전28의 api.js는 **Supabase /rest/v1/applications 직접 INSERT** 경로다. nexus-production Edge로 신청을 보내는 경로가 아니다.

- 따라서 직전 보고의 nexus-production CORS 제한을 현재 메인 신청 장애 원인으로 확정할 근거는 없다. Edge를 직접 쓰는 별도 기능은 따로 검증해야 하며 CORS를 변경하지 않았다.
- Python 정적 다운로드는 HTTPError로 실패했지만 브라우저 실제 화면과 저장된 배포 커밋을 확인했다. HTTPError를 사이트 전체 장애로 취급하지 않았다.

## 실제 확인한 결함
현재 배포된 **dist/admin.js**에 다음 경로가 있다.
1. processNew가 30초마다 신규 신청을 조회한 후 free.plan/free.assign을 호출.
2. planControls가 신청 카드 표시 시 자동으로 plan/assign 실행.
3. dist/free-workflow.js의 assign은 기존 작업을 plan.id 기반 idempotency_key로만 조회. 서버의 application_id/free_plan_id 연결 작업을 놓칠 가능성이 있어 기존 무료 작업과 중복 생성 위험이 있다.
