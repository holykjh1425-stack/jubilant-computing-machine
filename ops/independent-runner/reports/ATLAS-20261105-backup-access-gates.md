## 3. 공식 Pro 복구 경로와 선택
공식 자료 확인일 2026-11-05:
- https://supabase.com/docs/guides/platform/backups
- https://supabase.com/docs/guides/platform/clone-project
- https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore

Pro 일일 백업은 최근 7일 접근을 제공하지만, 이 프로젝트의 실제 복구점 존재/시각/유형은 미확인이다. 물리 백업을 다운로드 가능한 논리 덤프로 가정하지 않는다. 일반 운영 프로젝트 복원은 중단을 일으키므로 실행하지 않는다.

새 프로젝트 복원은 DB와 Auth 데이터 및 암호화 루트키를 복제하는 공식 경로다. 다만 추가 프로젝트 비용이 발생하며 Storage 파일·Edge·Auth/API 설정 등은 별도 구성이다. 특히 cron/net 등 외부 동작이 복원 직후 실행될 수 있어 현재 무송신·비과금 조건에 자동 적합하지 않다. 이번에는 생성하지 않았다.

우선안은 **기존 보호 Windows 환경에서 유효한 공식 DB 접속 수단을 이용한 TLS 검증 논리 덤프 → 공개키 스트리밍 암호화 → 보호된 기존 로컬 대상 복원**이다. DB 비밀번호 재설정/SSL 변경/새 토큰 발급으로 우회하지 않는다. 기존 자격증명을 찾지 못하면 이 경로는 차단 상태를 유지한다. 논리 복원은 Vault 루트키를 자동 이전하지 않으므로 별도 보호 복구가 해결되기 전 전체 복구 PASS를 선언하지 않는다.

문서의 파일 덤프 예제를 평문 저장으로 그대로 실행하지 않는다. 역할 암호와 Vault 등 별도 비밀 복구 범위를 명시해야 한다. 별도 덤프 간 시점 차이를 막기 위한 일관성 전략도 실행 전 확정해야 한다.

## 5. 실제 백업·복원 검증의 실행 조건
- 실제 데이터는 공개 GitHub/Actions 로그·아티팩트에 넣지 않는다. 공개 CI는 합성 데이터에만 사용한다.
- 개인키는 백업과 분리하고 Owner가 직접 관리한다. 개인키/암구호를 수집하지 않는다.
- 승인된 출력 폴더 ACL, 디스크 여유, 동기화 제외, 공개키 지문, TLS CA/호스트 검증, 실행 파일 무결성 및 DB 접속을 먼저 확인한다.
- 덤프 실패 또는 암호화 실패 시 즉시 중단하고 불완전 산출물을 성공 백업으로 표시하지 않는다. 암호화 출력 SHA-256·크기·시각·수신자 공개 지문·종료코드를 비밀 없는 manifest에 남긴다.
- SHA-256만으로 복호화/복원 가능성이 입증되지는 않는다.
- 복원 대상은 기존 운영 프로젝트와 다른 주소·볼륨·인증을 강제 확인한다. 외부 송신·cron·webhook·SMTP·실제 AI 공급자는 복원 전에 차단한다. 원본 고객 행에는 테스트 변경을 가하지 않는다.
- 복원 전후 비교는 전체 스키마·정책·권한·행 내용·시퀀스 및 기능을 포함한다. 승인 없는 차이는 실패로 처리하고, 합성 데이터 복원과 실제 운영 백업 복원을 구별한다.
- 필수 기능 확인은 격리된 합성 추가 데이터로 수행하고 실제 고객에게 메시지를 보내지 않는다.
- 종료 시 접근을 회수하고 복원 환경의 보호 보존 또는 승인된 폐기를 기록한다. SSD 평문 흔적은 단순 파일 삭제만으로 안전 폐기됐다고 주장하지 않는다.
- RPO: 복구 평가 시각과 실제 일관된 백업 시점의 차이. RTO: 복원 시작부터 필수 서비스 정상화까지 실측. 현재 두 값 모두 미측정이며 Pro 보존기간/제품 목표치를 실측값으로 쓰지 않는다.
