# SOLQ 보안 백업 잔여 준비 확정 — 2026-10-28 KST

기준: a391eb2. Windows 격리 합성 검증 11 PASS를 재사용한다. 테스트·로그인·인증·키 지문 확인을 반복하지 않았다. 이번 변경은 이 문서뿐이며, 기존 실행 스크립트는 변경하지 않는다.

## 1. 실제 접근 결과와 판정

현재 Work에서 접근 가능한 브라우저는 Chrome 하나이고 열린 탭은 0개이다. 네이티브 Windows PC 제어는 제공되지 않는다. 따라서 사용자 PC의 기존 Owner 세션, 로컬 인증서, 폴더, 볼륨, 설치 상태에 접근할 수 없다. 이는 사용자 PC에서 로그아웃되었다는 뜻이 아니다. 새 로그인이나 인증 요청을 하지 않았다.

| 항목 | 이미 확보한 근거 | 이번 잔여 판정 |
|---|---|---|
| 공식 연결 방식 | Direct 우선, IPv4 제약이면 공식 Session pooler. Connect 화면에서 실제 값을 취득해야 함 | 해당 프로젝트 Owner Connect 화면의 실제 선택값 확인 불가 |
| CA 출처·유효성 | 공식 Database Settings / SSL Configuration에서 얻은 CA와 verify-full을 사용하도록 기존 코드 구현 | PC CA 파일·공식 다운로드 출처·유효기간·실제 호스트 일치 검증 미확인 |
| C:\SOLQ_public_key | 기존 공개키 지문은 사용자 확인 완료, 실행 스크립트는 전용 로컬 경로 요구 | 전용 저장소 존재·공개키 포함·개인키 미포함 확인 불가 |
| C:\SOLQ_보안백업 | 폴더 생성은 사용자 확인 완료 | ACL·실제 여유 공간·동기화·재분석 지점 여부 확인 불가 |
| PostgreSQL 도구 | 사용자 PC pg_dump17.11 실행 확인 완료 | pg_dumpall·pg_restore17.11은 미확인; pg_dump 재검증 불필요 |
| 실제 PC TLS 연결 | 이전 MCP 연결은 서버17.11, TLS1.3 관측 | PC libpq의 verify-full 성공으로 대체할 수 없음; 실제 PC 연결 미실행 |
| 복원 환경 | 기존 합성 CI는 고객 데이터를 넣을 수 있는 보호된 복원 대상이 아님 | 기존의 승인된 비운영 대상이 확인되지 않아 준비 조건만 확정 |

공식 CA는 공개 인증서이지만, CA 파일이 존재하거나 만료되지 않았다는 사실만으로 출처·서버 신뢰를 확정하지 않는다. 체인 검증과 공식 호스트명 일치는 실제 TLS 연결에서 확인해야 한다. 인증서 오류가 나면 중단하며 sslmode=require/prefer/disable 또는 IP 치환으로 우회하지 않는다. SSL 강제 설정 변경은 데이터베이스 재시작을 유발할 수 있으므로 수행하지 않는다.

## 2. PC에서 한 번에 확인할 최소 항목 — 아직 실행하지 않은 체크리스트

기존 PC 로그인과 프로그램을 그대로 사용한다. 출력 전체나 접속 문자열을 채팅으로 복사할 필요가 없다. 판정 결과만 기록하면 된다.

1. Owner 대시보드의 기존 프로젝트 Connect에서 실제 방식이 Direct인지 Session인지 확인한다. IPv4 연결을 위해 새 유료 옵션을 구입하지 않는다. 지역을 추측해 pooler 호스트를 만들지 않는다. 비밀번호를 포함한 문자열은 저장·공유하지 않는다.
2. 공식 SSL Configuration에서 받은 CA의 출처와 인증서 유효기간을 로컬에서 확인한다. CA 파일 경로는 백업 스크립트의 sslrootcert에 사용하되, 실제 DB 연결은 별도 승인 범위로 남긴다.
3. C:\SOLQ_public_key의 존재, 검증된 기존 공개키의 포함, 개인키 미포함과 링크/리디렉션 부재를 확인한다. 이 점검으로 USB를 다시 연결하거나 개인키를 읽을 필요가 없다. 폴더가 없으면 미준비로 기록한다. 이번 작업에서 폴더·키를 생성/복사/가져오기하지 않았다.
4. C:\SOLQ_보안백업 속성의 보안 탭에서 소유자·상속·실제 접근 주체를 확인한다. 불필요한 Everyone/일반 Users의 읽기·쓰기 접근 여부를 검토하고, 사용자·SYSTEM·관리자 등 각 주체의 필요성을 판단한다. 이번 준비에서는 ACL을 바꾸지 않는다. 폴더 생성만으로 보호 완료로 인정하지 않는다.
5. 해당 볼륨의 여유 공간과 기존 디스크 암호화 상태를 확인한다. 허용된 백업 규모 산정이 아직 없으므로 임의의 고정 용량을 충분하다고 단정하지 않는다. 실패 후보·기존 정상본·암호화 보완분까지 함께 보관할 여유가 필요하다.
6. 경로가 OneDrive 등 동기화 범위·백업 도구·공유 폴더·재분석 지점으로 외부에 연결되는지 확인한다. 단순히 OneDrive 폴더 밖이라는 이유만으로 동기화가 없다고 인정하지 않는다. USB 개인키 백업은 대상에서 제외한다.
7. 이미 확인한 pg_dump는 반복하지 않고, 같은 PostgreSQL17 도구 폴더의 pg_dumpall 및 pg_restore에 대해 --version만 확인한다. 이는 DB 접속이 아니다. 도구가 없으면 별도 설치 승인 전 설치하지 않는다.

확인 항목의 최소 회신 형식: 연결 방식 / 공식 CA 준비·유효기간 확인 여부 / 공개키 전용 저장소 준비 여부 / 폴더 ACL 검토 여부 / 여유 공간·동기화 여부 / pg_dumpall·pg_restore 버전. 계정 암호·접속 문자열·키·개인 경로 목록은 불필요하다.

현재 기존 스크립트의 목적지는 암호화 .gpg/.partial.gpg 파일만 허용한다. 보완분이나 매니페스트도 예외 없이 암호화해야 한다. 암호문 해시만으로 완전성·복원 가능성을 판정하지 않는다.

## 4. 실제 고객 데이터를 사용하지 않는 격리 복원 준비 조건

아래는 실행 전 수용 기준이며, 이번에는 복원을 실행하거나 환경을 생성하지 않았다.

- 대상: 이미 존재하고 별도 승인된 비운영 환경. PG17 및 필요한 Supabase 역할·확장·Auth/Storage 함수와 호환되는 환경인지 확인한다. 단순 PostgreSQL만으로 Vault 등 모든 플랫폼 기능의 복구 PASS를 선언하지 않는다.
- 식별: 호스트·포트·DB·프로젝트 식별자가 운영 대상과 다르다는 점을 사전 확인한다. 운영 DB 주소·암호·Vault 키·고객 데이터는 넣지 않는다.
- 차단: SMTP·웹훅·pg_cron·무료/유료 워커·외부 AI 호출·Storage 전송·큐 재처리·복제의 자동 실행과 외부 송신을 차단한 상태를 입증한다. 운영 설정은 건드리지 않는다.
- 데이터: 새로 만들어진 합성 자료만 사용하고 실제 고객 행·암호 해시·실제 토큰·개인키를 복사하지 않는다. USB 복구키를 사용하지 않는다.
- 저장: 기존 보호된 저장공간에서 합성 덤프·복원 파일을 처리한다. 실제 운영 자료를 향후 취급하려면 디스크 암호화·접근 통제·메모리/임시파일 보호·용량 조건을 별도로 충족해야 한다.
- 검증 기준: 역할/의존성 → 스키마 → 데이터 → 제약·RLS·권한·함수·트리거·시퀀스의 적용 성공과 합성 자료 건수·내용 지문 일치를 확인한다. 비인가 읽기/쓰기 차단과 외부 호출0을 확인한다. 오류를 무시하거나 필요한 객체를 빼고 성공 처리하지 않는다.
- 한계: 합성 복원 PASS는 실제 운영 암호화 파일 복원 PASS가 아니다. 실제 복원과 USB 개인키 복구는 각각 별도 승인 대상이다. 현재 그 대상 환경의 존재·설치·차단 상태는 미확인이다.

## 5. 실행 결정과 승인

문서·범위·준비 조건 확정은 완료했다. 실제 PC 안전 연결 준비와 보호된 복원 대상 확인이 끝나지 않아 실제 운영 백업을 실행할 수 있는 상태로 판정하지 않는다. 이번에는 실제 백업 승인도 요청하지 않는다. 먼저 위의 최소 로컬 확인 결과가 필요하다.

실제 백업 승인 요청은 대상·범위·저장 위치·공개 수신키·접근 통제·공식 TLS·암호문만 저장하는 경로·비용/운영 부하·보완분 누락·중단 조건과 복원 목표가 구체화된 후 한 번에 제시한다. 현재 스크립트의 승인 스위치는 사용자 승인을 대체하지 않는다.
