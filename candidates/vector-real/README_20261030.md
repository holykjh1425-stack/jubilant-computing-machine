## 새로 확인·수정한 Vector0.58.0 호환성

Vector는list→inspect→follow logs와events를사용한다. list의Id/Names,inspect의Config.Image/Name/Created,event의Action/Actor.ID/Actor.Attributes를보존한다. 로그8byte프레임과RFC3339시각은바꾸지않는다.

Docker공식표는29.8까지이며29.8의하한은1.40(29.0~29.2는1.44)이므로모든29.x하한이같다고단정하지않는다. 사용자29.9.2의실API범위는아직미검증이다.

## 최소 실행 명령 — 아직 실행 금지, 별도 승인 후 PC에서만

## 실제 Vector 복구·배포와의 차이
기존중지Vector의Config.Env를바꾸는재생성없는경로는확인되지않았다. 이번Windows프록시는호스트읽기연결을검증하고즉시종료하는stage1후보다. Docker Linux컨테이너가Windowsloopback19443에접근할수있다는것까지증명하지않으며자동으로0.0.0.0바인딩을넓히지않는다.
실제로그수집은stage2:승인된별도native Windows Vector0.58.0프로세스또는독립검증컨테이너를후속검토할수있다. 원본14개보존을위해원본Vector를시작/재생성하지않는병행검증을우선한다. 허용할합성canaryID와대상image/digest/네트워크/PKI전달권한/정리대상을먼저확정하고별도승인받아야한다. 이번명령은새Vector프로세스/새Docker객체/기존로그읽기를실행하지않는다.
Vector자체는원래오류시backoff/retry할수있다. 여기서재시도0은프록시상위접속및route재전달에대한정책이며Vector바이너리자체에없는옵션을설정했다고주장하지않는다. 프록시는실패/중복stream을halt해backend재접속을차단한다.
