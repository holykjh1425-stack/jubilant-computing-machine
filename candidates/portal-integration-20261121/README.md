# SOLQ 통합 포털 후보

Windows Chrome에서 `index.html`을 파일로 열면 동작한다. 설치·서버·계정 연결 없이 합성 고객 A/B와 관리자를 전환할 수 있다. 상태와 요청 키는 페이지 메모리에만 남으며 새로고침 시 초기화된다.

## 후보 범위

| 파일 | 역할 |
| --- | --- |
| `index.html` · `portal.css` · `ui.js` | 반응형 상담, 접수, 합성 역할 선택, 신청 조회 및 상태 전이 |
| `vendor/solq-planning.js` · `vendor/dialogue.js` | 검증된 로컬 SOLQ 규칙형 엔진·상담 파일의 바이트 동일 복사본 |
| `service.js` · `client.js` | 인프로세스 API 모형 및 접수 키·응답 확인 클라이언트 |
| `review/portal-boundaries.REVIEW_ONLY.sql` | 별도 스키마·RLS·비공개 버킷 후보. 실제 적용 0건 |
| `verify/` | 합성 단위·API 모의·오프라인 브라우저 시험 |

P0-01과 P0-02에서 확인한 공식 Sites v32의 `app.js → api.js → /rest/v1/applications`와 기존 GitHub 루트의 `app.js → submit_application`은 각각 보존한다. 공식 `/privacy`와 `/admin`은 현재 배포와 연결된 경로다. 이 후보에서 기존 경로를 호출하거나 전환하지 않는다.

## 접수와 승인 흐름

상담 답변에서 규칙형 6단계 계획을 미리 볼 수 있다. 신청 원본에는 서비스 유형과 합성 설명을 저장한다. 개인정보 수집과 국외 이전에 대해 각각 시험 고지 버전, 원문 SHA-256, 선택 값, 서버 기록 시각을 증빙한다. 화면 문구는 합성 시험 안내다. 운영 활성화에는 별도 승인 고지 원문과 빌드 바이트 검증이 필요하다. 기록 시각은 서버 기록 시점으로, 고지 열람 시각 추정에 사용하지 않는다.

`submit`은 합성 세션의 고객 ID와 요청 UUID를 키로 사용한다. 동일한 정규화 원본 및 두 동의 지문은 기존 신청 ID와 접수번호를 반환한다. 원본·동의 변경은 `409 REQUEST_CONFLICT`로 차단한다. 번호와 신청 ID는 모두 고유하며 충돌 시 최대 4회 할당한다. 기존 원본을 덮어쓰지 않는다. 합성 서비스는 ID·번호·요청 인덱스의 일치를 확인한 뒤 저장 응답을 반환한다. 클라이언트는 저장 확인 플래그, 요청 ID, 지문, 신청 ID와 접수번호 형식을 모두 대조한다. 전송 실패나 응답 유실이면 동일 키·동일 원본을 보존하고 성공 표시를 보류한다. 새 신청은 저장 확인 후 명시적으로 준비한다. 운영용 재접속·다중 탭·트랜잭션과 독립 세션 커밋 확인은 기존 P0 보완 후보를 적용할 별도 환경에서 검증한다.

관리자는 합성 세션에서 신청을 조회하고 무료 계획을 저장한 뒤 기본형 100,000원 견적을 발행한다. 고객은 자기 신청의 유효 견적 버전에 동의한다. 관리자는 같은 버전에서 착수금 30,000원 모의 확인 후 별도 제작 승인을 기록한다. 잔금 70,000원은 안내로만 표시한다. 견적이 갱신되면 이전 버전 동의는 효력을 잃고, 입금 확인 후 견적 변경은 차단한다. 모의 관문을 모두 통과해도 `checkExecution`은 비활성 상태를 반환한다. 제작 워커·결제·유료 API·외부 발송 경로는 없다.

## 역할과 공급자

브라우저의 역할 선택은 합성 세션 발급 도구다. 실제 인증을 표시하거나 인증 데이터와 접속하지 않는다. API 모형은 매 호출에서 만료된 세션을 거부하고 소유자와 관리자 범위를 검사한다. 역할 선택형 브라우저의 메모리는 실서비스 보안 경계가 될 수 없다. SQL 후보의 RLS는 로그인 사용자의 행 조회에만 권한을 부여한다. 접수와 상태 전이는 신뢰된 서버 계정에 한정하도록 모델링했다. 운영 구현에서는 요청마다 서버 측 Auth·관리자 소속·소유권을 독립 확인하고 원본·두 동의·상태 기록의 거래 단위를 검증해야 한다.

계획 공급자는 `makePlan(input)` 인터페이스로 분리되어 있다. 기본 `rules`는 기존 엔진을, `mock`은 고정 합성 단계를 반환한다. 등록된 두 공급자 외에는 실패한다. 추후 새 공급자 도입은 별도 승인 아래 서버에서만 구현한다. 브라우저의 공급자 선택, API 키, 실제 생성형 AI 호출은 이 후보에 포함되지 않는다.

## 재현과 원복

```text
node --test verify/service.test.cjs
node verify/browser.cjs
```

브라우저 시험은 기존 설치 Chrome을 파일 URL 및 CDP 파이프로 사용한다. 이번 P0 후보와 직접 관련된 검증만 수행한다. 공개 운영 페이지, Supabase, 데이터 파일, 고객 정보에는 접속하지 않는다.

운영 적용 전 승인된 고지 원문, 보호된 PG17/PostgREST/Auth의 실제 권한·독립 세션·동시성 및 관리자 종단 시험, 최신 전체 백업과 동일 ID 격리 복원, RPO/RTO, 보안 경고 및 회귀 확인이 필요하다. 운영 전환과 Sites 배포는 별도 승인 대상이다. 후보 롤백은 필요 시 개발 브랜치에서 추가 커밋을 되돌리고 후보 URL 사용을 중지하는 방식으로 진행한다. 기존 운영 제출 경로를 다시 활성화하거나 운영 DB를 복원하는 변경은 이 원복에 포함되지 않는다. SQL 서브시스템은 미적용이므로 이번 변경에 대한 DB 원복은 없다.
